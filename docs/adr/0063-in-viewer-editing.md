# ADR-0063: In-viewer editing on the viewer origin

- **Status**: Accepted — implementation gated on a `/security-review` pass before the implementation PR ships (amends ADR-0038)
- **Date**: 2026-07-07
- **Deciders**: agranado2k
- **Relates to / amends**: ADR-0038 (report viewer access & serving — **amends** it by adding a second, authenticated route profile to the viewer origin), ADR-002/ADR-013 (viewer origin isolation + security-header stack, unchanged for the public route), ADR-014 (service-worker block, unchanged), ADR-0037/ADR-0062 (upload/versioning pipeline + the ProseMirror editing model this route serves), ADR-0056 (report sharing & ACLs — access-token/unlock-cookie precedent this ADR's edit token rhymes with), ADR-0059/ADR-0060 (owner + write-grant authorization, re-checked per save), ADR-0051 (MCP OAuth 2.1 / API-key auth — no anonymous writes on any surface), ADR-012/ADR-0045 (scan gate — every save re-enters it).

## Context and problem statement

`view.<domain>/<slug>` (ADR-002/0038) is a deliberately credential-free, PSL-isolated origin that serves raw, untrusted report bytes under a strict sandbox CSP with no first-party JS and the service-worker block (ADR-014). That isolation is the whole security model: a malicious report can't reach app credentials or persist itself, because there's nothing on that origin to reach.

The editing epic (ADR-0062: a ProseMirror-based editor for report content, informed by the `spike/DECISION.md` verdict) wants users to edit their report *in place*, ideally without leaving the viewer's rendered context. That means putting an authenticated, first-party JS application — the editor — on the same origin that today exists specifically to have none. This is the central tension this ADR resolves, and it was flagged explicitly in PR #144 review: **does the enforcing/sandbox CSP have to be relaxed for the editor, and if so, how is that contained?**

## Decision drivers

- Preserve the ADR-002/013/0038 isolation guarantee for the existing public read path — zero regression, zero exception.
- Give the editor a first-party JS surface without turning the whole viewer origin into an authenticated app.
- Never let the editor execute the untrusted report bytes it's editing — those bytes are exactly what the isolation model doesn't trust.
- Reuse proven machinery (ADR-0056's app-mints/viewer-verifies token pattern) instead of inventing a new trust primitive.
- Every write path (dashboard, viewer edit route, MCP, ADR-0051) enforces auth and `canWrite` (ADR-0059/0060) server-side — UI is never the boundary.
- Ship gated on independent security review, given the sensitivity of adding auth + JS to an intentionally-bare origin.

## Considered options

- **Two CSP profiles on one origin, edit route only** *(chosen)* — public route (`GET /<slug>`) stays exactly as today; a new `GET /<slug>/edit` route serves the editor under a separate, controlled CSP. Only the edit route ever gains first-party JS.
- **Relax the public route's CSP to allow the editor bundle everywhere** (rejected — reopens the sandbox for every reader of every report, not just an authenticated owner/grantee actively editing; the isolation guarantee would degrade to "usually not exploited" instead of "structurally can't be").
- **Move editing entirely to the dashboard origin (`app.<domain>`), no in-viewer editing** (documented as the fallback — see Decision 3 — preserved as the answer if security review rejects the in-viewer route).
- **Full Clerk session on the viewer origin** (rejected — see Decision 3).

## Decision outcome

### 1. The CSP question, answered up front

The enforcing/sandbox CSP for the **public** route does **not** relax, at all. A second, separate CSP profile is introduced, scoped **only** to the new `GET /<slug>/edit` route:

- `script-src 'self'` — first-party editor JS only, nothing report-supplied; no `unsafe-inline`, no `unsafe-eval`. (Superseded the original "plus build-time hashes" wording: the implementation ships the *stricter* bare `'self'`, since this repo's Remix/React stack already hydrates without inline scripts — see `appHeaders()`. A per-response nonce, not hashes, is the documented path if a future editor build step ever needs an inline allowance; flagged for `/security-review`.)
- `connect-src` limited to the app-origin API (`app.<domain>/api/v1/...` — the token-mint and save endpoints), nothing else.
- `worker-src`, `frame-ancestors`, `object-src`, and the rest of the ADR-013 stack carry over from the public profile — the edit route is *additive* (it gains a script allowance the public route doesn't have), never a general loosening.
- The two profiles are selected by route, computed independently, and there is no code path where a public `GET /<slug>` request can receive the edit-route CSP or vice versa. e2e security-header tests assert both profiles independently (see Consequences).

This containment is the answer to the PR #144 question: yes, the sandbox CSP is relaxed, but *only* for one authenticated route, *only* for a first-party bundle, and the public read path — still the overwhelming majority of viewer traffic — is untouched byte-for-byte.

### 2. Two route profiles, never mixed

- **`GET /<slug>` (public, unchanged)**: no auth, no first-party JS, the existing strict sandbox CSP, the ADR-014 service-worker block, the full ADR-0038 state machine (200/404/410/451, `noindex`). Nothing in this ADR touches this route's behavior or headers.
- **`GET /<slug>/edit` (new, authenticated)**: serves the editor application bundle under the CSP profile in Decision 1. Requires a valid edit token (Decision 3). The edit route is the **only** place the viewer origin gains first-party JS or an authenticated session concept — no other route on `view.<domain>` changes.

### 3. Auth: a scoped edit token, minted by the app

Chosen mechanism, deliberately rhyming with ADR-0056's access-token / unlock-cookie pattern: the dashboard (`app.<domain>`, Clerk session) mints a **short-lived, single-report, single-purpose edit token** when a user with `canWrite` on a report (ADR-0059/0060: `isOwner OR hasWriteGrant`) opens the editor. The viewer's edit route validates the token's signature and scope (slug-bound, purpose-bound, exp-bounded — same HMAC-compact codec family as the `Access token`), then **re-checks `canWrite` server-side on every save**, not just at token-mint time — a grant revoked mid-session stops working on the next write, not just the next token mint.

Considered and rejected:
- **Full Clerk session on the viewer origin** — would put the entire authenticated session (cookies, whatever Clerk needs client-side) on the untrusted-content origin, enlarging the blast radius of any future viewer-origin compromise to "attacker can act as the signed-in user," not just "attacker can read/write via a narrow, purpose-bound token." Rejected outright, independent of the security-review outcome.
- **Dashboard-origin editing with a deep-link fallback** — edit entirely on `app.<domain>` (which already has Clerk + full first-party JS), with the viewer's `/edit` route (if it exists at all) merely deep-linking there. Documented here as **the fallback if `/security-review` rejects in-viewer editing** — it preserves the UX goal (one click from the report to editing it) at the cost of leaving the viewer origin's read-only posture completely alone, at zero new viewer auth surface.

### 4. Saves re-enter the existing pipeline — no mutate-in-place

An edit-save does not mutate stored bytes directly. It produces a **new `ReportVersion`** through the same R2-first/commit-last pipeline as any other upload (ADR-0037, and the versioning extension in ADR-0062): write to R2, run the ADR-012 scan gate, and only promote to `live_version_id` on a `clean` verdict (ADR-0045's async pipeline). A malicious or corrupted edit cannot go live unscanned — the scan gate that already protects uploads protects edits identically, with no special-case bypass for the edit route.

### 5. No anonymous writes, on any surface

Enforcement of auth and `canWrite` lives server-side in the use cases (401 unauthenticated / 403 not-authorized), independent of transport: the REST API, the new viewer edit route, and MCP (ADR-0051 — every MCP write call carries OAuth 2.1 or an `arp_` API-key Bearer) all funnel through the same authorization check. UI-level hiding of the edit affordance is never treated as a security boundary. Correspondingly, the **public** `GET /<slug>` route never serves editor JS, comment data (ADR-0064), or any edit affordance — those exist only behind `/edit`.

### 6. ADR-014 is unchanged, including for future collaboration

The service-worker registration block stays in force on the viewer origin, for both routes, with no carve-out for the edit route. This includes any future real-time collaboration transport (ADR-0067, not yet written) — a collab layer must not register a service worker on `view.<domain>` to get around this; if it needs background delivery, it does so through the app-origin API, not a viewer-origin service worker.

## Consequences

**Positive**

- The public read path — still most of the traffic — is provably untouched: same CSP, same headers, same state machine, same absence of JS.
- The isolation break is contained to exactly one route, one CSP profile, and one narrowly-scoped token — not a general credential.
- Saves reuse the existing scan-gated, versioned pipeline; there is no new "fast path" that skips moderation.
- Rhyming the edit token with the ADR-0056 access-token codec means no new signing primitive, just a new claims shape and purpose tag.

**Negative / risk delta (stated honestly)**

- The viewer origin gains an authenticated, first-party-JS-bearing route for the first time since ADR-002. This is a real, non-zero increase in that origin's attack surface, even though it's contained to `/edit`. That is exactly why this ADR's Status is gated on an independent `/security-review` pass before the implementation PR ships — this document records the intended design, not a green light to build without that review.
- e2e security-header tests must now cover **both** CSP profiles explicitly (today's suite only asserts the public stack, ADR-013) — a regression that silently applies the edit-route CSP to the public route (or vice versa) must fail CI.
- If a report is ever submitted to the Public Suffix List (PSL) as a distinct isolation boundary, the existence of an authenticated sub-route under the same eTLD+1 as the public content is a fact that submission reviewers may reasonably ask about; this ADR is the reference for how the exception is bounded.
- The dashboard-origin fallback (Decision 3) is a real, ready-to-ship alternative if security review finds the in-viewer token model unacceptable — it is not a hypothetical, it should be treated as a live option during that review.

## More information

- Implementation: the edit-route CSP profile and its e2e header assertions live alongside the existing ADR-013 `secureHeaders()` helper (as a second, route-selected profile, not a fork); the edit-token codec extends the ADR-0056 `packages/domain/src/signed-token.ts` shared primitive with an `edit` claims shape (slug, purpose, exp) parallel to `AccessClaims`.
- **Edit-token codec — implemented (Phase 2, `packages/domain/src/edit-token.ts`)**: `EditClaims { slug, exp, sub, scope: "edit" }`, built on the shared `signed-token.ts` primitive, mirroring `access-token.ts`'s structure exactly (`mintEditToken`/`readEditToken`/`verifyEditToken`). Single-report via `slug`; short-lived via `exp` (suggested 15–30 min TTL — shorter than the owner `Access token`'s 24h, since edit is a higher-privilege capability than read; the exact constant is deferred to the mint site); carries the acting user via `sub` (required, non-empty — an edit token with no bound subject isn't a valid capability); single-purpose via the `scope: "edit"` literal discriminant, which is the security boundary that prevents token confusion — `parseEditClaims` is strict enough that a validly-signed `Access token` (even an `owner: true` one, sharing the same HMAC secret) cannot narrow into `EditClaims`, because `AccessClaims` has neither `sub` nor `scope`. Verified by a dedicated cross-parse-rejection test (`edit-token.test.ts`) that mints a real access token via `mintAccessToken` and asserts `readEditToken` rejects it. The view origin verifies signature + scope only (never holds Clerk creds); `canWrite` re-check on save and the `/edit` route wiring are still pending (next phase), along with the app-side mint-into-the-open-flow.
- **Edit-route CSP profile — implemented (Phase 3, `packages/headers/src/view-headers.ts`)**: `editViewHeaders({ appOrigin, reportToUrl? }): Headers`, a second, route-selected profile alongside the existing `viewHeaders()` (the public profile's byte-for-byte output is unchanged — pinned by a regression test). `appOrigin` is REQUIRED (the app-origin API the edit token authenticates against). Both profiles share their unrelated directives (`default-src`, `img-src`, `font-src`, `frame-ancestors`, `base-uri`, `form-action`, `object-src`, `worker-src`, `report-to`) via one internal `CSP_SHARED` table, so they can't silently drift on the directives that are supposed to stay identical. Every relaxation vs the public profile, and its rationale:
  - **No top-level `sandbox` CSP header** — the single biggest relaxation. The public profile pairs its enforcing CSP with a second `sandbox` header because the top-level document IS the untrusted report; the edit route's top-level document is instead the TRUSTED first-party editor app (Remix/React), which needs same-origin DOM/storage and to call the app-origin API, so sandboxing it would break it and buys nothing security-wise the isolation model needs. Containment of the untrusted report being edited does NOT depend on this: the report renders inside the editor's own sandboxed `srcDoc` iframe (`sandbox="allow-same-origin"`, no `allow-scripts`), which carries its own, independently enforced, more restrictive `<meta>` CSP (`default-src 'none'; style-src 'unsafe-inline'; img-src data: …` — `apps/app/app/editor/iframe-document.ts`).
  - **`connect-src 'self' <appOrigin>`** — widened by exactly one explicit, caller-supplied origin (never `'*'`), so the editor's first-party JS can reach the edit-token-authenticated app-origin API.
  - **`script-src 'self'`** — NOT loosened to `'unsafe-inline'`. This mirrors `appHeaders()` (`packages/headers/src/app-headers.ts`), which already ships `script-src 'self'` with no `'unsafe-inline'` for the same Remix/React stack on the dashboard origin, i.e. this repo's own Remix build doesn't need an inline-script allowance to hydrate. No `'unsafe-inline'` was needed.
  - **`frame-src 'self'`** — a NEW directive the public profile doesn't have at all, required so the editor's own `srcDoc` report iframe is permitted to render (browsers resolve a `srcDoc` frame's effective origin to its embedder's for `frame-src` matching purposes; no `blob:`/`data:` needed since the iframe is only ever given `srcDoc` markup, never a `blob:`/`data:` URL).
  - **`Cache-Control: no-store`** (vs the public route's `private, max-age=60, must-revalidate`) — authenticated, per-user route; nothing about it should be cached.
  - Everything else — `default-src 'self'`, `style-src 'self' 'unsafe-inline'` (Tailwind), `img-src`, `font-src`, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'self'`, `object-src 'none'`, `worker-src 'self'`, the report-only shadow policy, COOP/CORP/Origin-Agent-Cluster/Referrer-Policy/Permissions-Policy/nosniff/HSTS/Report-To — is IDENTICAL to the public profile: additive, never a general loosening, matching this ADR's Decision 1.
  - **OPEN for `/security-review`** (flagged, not resolved by this phase): (1) whether "top-level document not sandboxed" is acceptable given the editor is the first `first-party-JS-bearing`, authenticated route ever added to `view.<domain>` (the Consequences section's stated risk delta); (2) confirm in real target browsers that `frame-src 'self'` is sufficient for the `srcDoc` iframe (historically inconsistent across implementations) before this profile is wired to a route. `script-src 'unsafe-inline'` was NOT used, so it is not an open item — noted here only because the implementation prompt asked to flag it if used.
  - **No route wires this profile yet.** `editViewHeaders` is a pure, unit-tested header builder with no caller — it is inert in production until the `/edit` route (Phase 4) selects it, and the full `/security-review` pass this ADR's Status gates on runs against that wired surface, not this function in isolation.
- **Signing-secret trade-off (flagged, not decided)**: should the edit token use a signing secret separate from the `Access token`'s (`VIEW_ACCESS_TOKEN_SECRET`), for defense-in-depth key separation between the read/share and edit capabilities? Default taken here is to **reuse the shared secret**, because the `scope: "edit"` discriminant already makes cross-token confusion structurally impossible at the parse layer (see above) — a separate secret would add operational surface (another rotation, another env var, another place the app and view must agree) without closing a gap the scope check doesn't already close. The case *for* a separate secret: if the shared secret ever leaks, blast radius is identical either way (an attacker who can forge one can forge the other), so key separation only helps if the two secrets are rotated/scoped independently in practice (e.g. edit token issuance restricted to a narrower app code path). Left for the reviewer/mint-phase implementer to weigh; no runtime behavior depends on this yet since minting doesn't ship in this phase.
- ADR-0062 owns the ProseMirror schema and the parse-to-model / model-to-HTML boundary this route relies on (Decision 2 of this ADR: the editor renders the model, never the raw blob).
- **Edit-token API acceptance seam — implemented (this API slice, HTTP endpoints for Decision 3's dashboard fallback)**: the `canWrite` re-check on save (Decision 3/4) and "no anonymous writes, on any surface" (Decision 5) are now wired end-to-end on the app-origin REST API, so a cross-origin caller on `view.<domain>` (the dashboard-fallback deep link's eventual in-viewer editor client, or any bearer of a minted edit token) can drive an edit session entirely over HTTP:
  - **Acceptance boundary**: `resolveEditTokenActor` (`apps/app/app/server/edit-token-actor.server.ts`) is the LAST front door tried by both `resolveUploadActor` and `resolveActorForRead` (`apps/app/app/server/auth.server.ts`), gated on the route actually having a `:slug` param — a route with no slug (e.g. `/api/v1/keys`) never reaches it, so it can't become a general Clerk bypass. It re-verifies the token's signature/scope/expiry AND re-runs `loadWritableReport`'s LIVE `canWrite` check (a grant revoked after mint rejects on the very next call, not just the next mint) — never trusts the token's mere validity as proof of CURRENT authorization.
  - **Scope, deliberately narrow**: an edit-token actor is granted `["reports:write"]` ONLY — never `acl:write`. It can save content, list/read versions, and read/write comments on the report it's bound to; it can NOT grant/revoke write access, read/write the ACL, move, rename, or delete the report, or act on any other report (the token is slug-bound; a route's raw `:slug` path segment must be the CANONICAL slug the token was minted for, or `resolveEditTokenActor` rejects the mismatch).
  - **Endpoints accepting the edit token** (all under `/api/v1/reports/{slug}/...`, `{slug}` = the canonical slug): `POST .../versions` (save an edit as a new `ReportVersion`, `origin: 'editor'` — never a create path, always via `updateSlug`), `GET .../diff?from=<version_id>&to=<version_id>` (JSON structural/fallback diff between two versions — **note for the 4c client**: the diff payload contains HTML *derived from stored report bodies*, so when the view-origin editor renders it, it MUST flow through the same sandboxed-iframe + CSP the viewer applies (ADR-013) and the service-worker block (ADR-014); rendering it unsandboxed or on the app origin would reintroduce exactly the XSS/cookie-theft exposure the view-origin split exists to prevent — claude-review #183 F-1), `GET .../comments` + `POST .../comments` (list / add / reply), `PATCH .../comments/{comment_id}` (resolve), `GET .../versions` (list). The comments/versions GET+POST surfaces were already auth-agnostic (built on the `resolveActorForRead`/`resolveUploadActor` seam before this slice existed) — this slice added CORS to them and confirmed the edit-token path end-to-end; the save and diff operations are new.
  - **CORS posture (security-critical)**: `Access-Control-Allow-Origin` is the EXACT configured `VIEW_ORIGIN` (read from `defineEnv()`, never the request-origin-fallback `viewOrigin(request)` helper used for building absolute URLs elsewhere — that fallback would make the allow-list trivially self-satisfying), echoed only when the request `Origin` matches byte-for-byte — never `*`, never a reflected arbitrary origin, and never any origin at all when `VIEW_ORIGIN` is unset (fails closed, same posture as the edit-token secret itself being unset). `Access-Control-Allow-Credentials` is NEVER set. `Access-Control-Allow-Headers: Authorization, Content-Type` and a resource-specific `Access-Control-Allow-Methods` answer the `OPTIONS` preflight (204, no body) BEFORE any auth runs — a preflight carries no `Authorization` header by construction, so it must never touch the DB. The preflight advertises `Access-Control-Max-Age: 600` (caches only the origin-independent method/header allow-list — never a credential — so the editor skips a redundant round-trip per call). The wrapper **merges** `Vary: Origin` into any `Vary` the handler already set rather than overwriting it (a clobber could drop a handler's own `Vary: Accept-Encoding` and poison a shared cache). Implemented as a pure header-decision module (`packages/http/src/cors.ts`) plus a route wrapper (`apps/app/app/server/cors.server.ts`, `corsRoute`), unit-tested for the matching/non-matching/preflight/`Vary`-merge matrix.
  - **Why no CSRF concern despite the relaxed CORS**: auth here rides a custom `Authorization: Bearer <editToken>` header, never an ambient cookie. A cross-site request forger can make the browser SEND a request, but cannot make it carry an app-origin bearer token it has no way to read — and `Access-Control-Allow-Credentials` being unset means even a same-origin-looking cookie-based session never rides along on a cross-origin call to these routes. This is the same rationale ADR-0056's access-token / unlock-cookie precedent established for token-based capabilities.
- `docs/context-map.md` / `docs/domain-glossary.md`: no new bounded context here — this is a serving/access-model decision inside Reports & Folders, alongside ADR-0038/0056. Any new terms this ADR needs (e.g. **Edit token**) are added to the glossary in this PR's integration step, per the CLAUDE.md same-PR rule.
- **The unified experience — implemented (client, on top of the 4c-2a auth seam + editor + save)**: `GET /<slug>/edit` now renders a single, app-styled surface — the **Unified experience** (glossary term added, see `docs/domain-glossary.md`) — combining editing, a read-only View mode, Comments, and Compare (version diff) behind the one auth seam Decision 3 already established. Nothing about the auth decision, the edit-token codec, or `editViewHeaders`'s CSP changed to ship this — it is purely additive UI + client-side data flow on top.
  - **Layout**: a top `TopBar` (brand · doc title · a View⇄Edit toggle, replaced by "← Back to document" while comparing · Comments/Versions tab buttons · Save) plus ONE left panel, tabbed Comments | Versions, **hidden by default** — the document is the dominant element until the user opens a tab, at which point the panel slides in alongside it. `ReportEditor` stays mounted at ALL times (even while the user is in View or Compare) and is only hidden via CSS (`hidden`) rather than unmounted — switching modes never re-triggers `initialDoc`, so in-progress, unsaved edits survive a round trip through View/Compare back to Edit.
  - **View mode**: a READ-ONLY render of the CURRENT (possibly unsaved) editor content — a snapshot taken at the moment the user clicks "View" (`serializeBody(docRef.current)` → `reinjectShell(shell, …)`, `arp-report-html`), not continuously re-rendered while editing.
  - **F-1 (the hard security constraint)**: View mode and Compare BOTH render their assembled HTML through a NEW `buildReadOnlyIframeDocument` (`packages/editor/src/iframe-document.ts`, exported from `arp-editor` alongside the existing `buildIframeDocument`) — the SAME comment-aware-parse + locked-`<meta>`-CSP mechanism `ReportEditor`'s own sandboxed iframe uses, refactored into a shared `injectCspIntoParsedDocument` helper so both entry points are provably identical on the security-relevant behavior (verified by a parallel adversarial test suite — decoy `<head>` in a comment, decoy `</head>` in a comment, `<head>`-shaped attribute values — mirroring `buildIframeDocument`'s own coverage). The one difference: `buildReadOnlyIframeDocument` takes an ALREADY-ASSEMBLED full HTML document (typically `reinjectShell(shell, bodyHtml)`) and PRESERVES its body content, since there is no ProseMirror mount to populate it — `buildIframeDocument` still always yields an empty body for PM to mount into. The client component (`apps/view/app/edit/components/SandboxedHtml.tsx`) renders the result in an iframe with `sandbox=""` — stricter than `ReportEditor`'s `sandbox="allow-same-origin"`, since nothing here ever needs `contentDocument` access (a pure static render, no DOM reach-in). Neither View mode nor Compare ever uses `dangerouslySetInnerHTML`, and both render on the VIEW origin exclusively — never proxied through or re-rendered on `app.<domain>`.
  - **Comments tab**: the initial list is loaded in the route LOADER via a server-to-server Bearer fetch to `GET {appOrigin}/api/v1/reports/{slug}/comments` (`apps/view/app/edit/comments-client.ts` — no CORS involved, this is Vercel-function-to-Vercel-function). Add/reply/resolve are CLIENT-side cross-origin `fetch`es carrying the SAME edit token as `Authorization: Bearer` (`credentials: "omit"`, copying `../edit/save-edit.ts`'s pattern exactly) — `CommentsPanel`/`CommentThread`/`NewCommentComposer` (`apps/view/app/edit/components/CommentsPanel.tsx`) are modeled on `apps/app/app/components/CommentSidebar.tsx`'s structure but use `fetch`, not Remix `useFetcher` (there is no same-origin resource route on this app to fetch against). Comment bodies render as plain React text — never HTML — since they're untrusted user input. Selection→anchor wiring reuses `arp-editor`'s `buildSelectionAnchor` + `ReportEditor`'s `onSelectionChange`, gated to `mode === "edit"` (selection tracking needs the mounted `EditorView`). Resolved/highlighted comments feed back into `ReportEditor`'s `comments` prop directly — the wire `CommentWire` shape (`id` + `anchor.relative`) is structurally identical to `CommentForHighlight`, no mapping needed.
  - **Versions tab**: loaded in the loader the same server-to-server way (`apps/view/app/edit/versions-client.ts`, `GET .../versions`), rendered with each version's `uploaded_by` (a `user_…` External Id — the wire projection exposes no email) + `uploaded_at` + `scan_status` + `origin`. The tab also hosts Compare: two `<Select>`s (From/To) plus a Compare button that fires a CLIENT-side `GET {appOrigin}/api/v1/reports/{slug}/diff?from=&to=` (`apps/view/app/edit/diff-client.ts`, same Bearer pattern) and hands the resulting `DiffWire` up to the route component, which switches to `mode: "diff"` and renders it via `SandboxedHtml` per F-1 above.
  - **Loader data-assembly**: a failed Comments/Versions load degrades to an empty list rather than crashing the editor (`apps/view/app/edit/loader-data.ts`'s `buildEditLoaderExtras`, unit-tested) — mirrors the loader's existing "can't load this bit, don't break the page" posture for `resolveViewableReport`'s non-`"serve"` outcomes.
  - **Test coverage**: every cross-origin fetch helper (`comments-client.ts`, `versions-client.ts`, `diff-client.ts`, and the shared 401/403→"session expired" mapper `http.ts`) is unit-tested with an injected `fetchImpl`, mirroring `save-edit.test.ts`'s existing pattern; `buildReadOnlyIframeDocument` has its own adversarial CSP-injection suite alongside `buildIframeDocument`'s. UI components stay e2e/dogfood territory (no jsdom tier in this repo's Vitest config, matching `apps/app`'s own convention of not render-testing its own components).
  - **The interim `_index.tsx` hydration-smoke-test landing page (a dev click-counter) is retired** — the viewer origin's `/` now renders a clean, on-brand explainer with no dev affordance.
- **Phase 5 — the app-origin cutover: owners join the unified experience, plus a silent-refresh endpoint (implemented, flagged for `/security-review`)**: two SECURITY-SENSITIVE changes on the app origin, both gated behind the SAME `canWrite` (`isOwner OR hasWriteGrant`, ADR-0060 §4) and edit-token machinery this ADR already established — no new trust primitive, no change to the edit-token codec or `resolveEditTokenActor`'s trust logic.
  - **Owner routing collapses into ONE gate.** `GET /reports/{slug}/open` (`ownerOpenLocation`, `apps/app/app/server/open-report.server.ts`) used to be two-tier: the report's OWNER got a 24h `owner:true` `Access token` and the OLD read-only viewer (`${viewOrigin}/${slug}?access=...`); a non-owner write-grantee got the 15-min `scope:"edit"` token and the unified `/edit` experience. Phase 5 retires the owner-only tier: `loadWritableReport` (the SAME `isOwner OR hasWriteGrant` gate) is now the ONE check, and EVERY canWrite user — owner or grantee, no distinction — is minted the SAME `scope:"edit"` token and redirected to `${viewOrigin}/${slug}/edit?et=...`. An owner opening their own report now lands in the unified in-viewer experience (View/Edit/Comments/Compare) exactly like a write-grantee already did — there is no longer a separate, higher-privilege capability minted from this route. Mitigations, all already in place and independent of this endpoint: **(a)** single-report, `reports:write`-only scope (`EDIT_TOKEN_SCOPES`, `auth.server.ts`) — never `acl:write`, so a thief can edit that one report's content, nothing else (can't reshare, delete, move, or touch any other report); **(b)** the LIVE `canWrite` re-check on EVERY refresh (not just the original mint) — revoking the grant or transferring ownership cuts the thief off within one remaining TTL (≤15 min) of their last successful refresh, not up to 24h; **(c)** the token only ever leaves the app on the view origin's strict edit-route CSP (Decision 1) + sandboxed report iframe (§F-1) — the control that's actually supposed to keep it out of an attacker's reach in the first place, this endpoint doesn't add a new place for it to leak from.

- **Phase 5-D — the ABSOLUTE session cap on edit-token refresh (implemented, closes the Phase 5 recommendation flagged for `/security-review` and claude-review #185).** Phase 5's silent-refresh endpoint bounds a REVOKED grant's exposure to within one TTL (mitigation (b) above), but did nothing for a grant that's NEVER revoked — an owner editing their own report, say — where a leaked edit token could previously be refreshed indefinitely. This phase caps the TOTAL length of a refresh chain, independent of revocation:
  - **New claim: `EditClaims.sessionStart`** (`packages/domain/src/edit-token.ts`) — epoch seconds of the FIRST mint of a refresh chain, carried forward UNCHANGED by every subsequent refresh (never reset). `mintEditToken` gains an OPTIONAL trailing `sessionStartSeconds?: number` parameter that DEFAULTS to `nowSeconds` — so every EXISTING mint site (`open-report.server.ts`'s `/open` mint) is unchanged and always starts a fresh session; only `refreshEditToken` ever passes an explicit (carried-forward) value. `sessionStart` sits inside the signed JSON payload like every other claim, so tampering with it (e.g. resetting it to dodge the cap) breaks the HMAC signature exactly like tampering with `exp` or `sub` would.
  - **Backward compat**: `sessionStart` is OPTIONAL in `parseEditClaims` — a token minted before this change has none, and still authenticates normally for save/comments/diff (no forced logout on deploy). Only the refresh path treats a MISSING `sessionStart` specially: fail closed (see below), rather than parse-reject it everywhere.
  - **`SESSION_CAP_SECONDS = 8 * 60 * 60`** (8h — a full workday of continuous editing; deliberately generous since it bounds total session length, not idle time, which the existing silent-refresh timer already handles well under this). Defined in `apps/app/app/server/edit-token-refresh.server.ts`, alongside the refresh logic it gates.
  - **Enforced ONLY on refresh** (`refreshEditToken`) — never on initial mint (`/open`) and never on save/comments/diff auth (`resolveEditTokenActor`/`readEditToken`), which only need an unexpired, correctly-scoped token. On refresh: denied when the presented token's `sessionStart` is missing (a legacy, pre-cap token — its true age is unknown, fail closed) OR `now - sessionStart >= SESSION_CAP_SECONDS`; both map to the existing `NotAllowed` (403) problem+json path `refreshEditToken` already used for a failed `loadWritableReport`, which the view client already treats identically to a 401 ("reopen this report from the dashboard" — the correct recovery, since re-opening mints a genuinely fresh session). A successful refresh mints the new token carrying `sessionStart` FORWARD UNCHANGED (never reset to `now`) — this is what makes the cap bound the WHOLE chain rather than resetting on every hop.
  - **How the presented `sessionStart` is recovered — Option (A) chosen.** The task brief posed two options: (A) keep the route on `handle({mode:"write"})` (as today — INTENTIONALLY any write actor, not edit-token-only, per the Phase 5 route's own documented rationale and claude-review #185 finding #1) and have `run()` independently re-read the `Authorization` Bearer header + `readEditToken` to recover `sessionStart`; or (B) restructure the route to be edit-token-only (`resolveEditTokenActor` directly), which would also flip that earlier claude-review #185 finding #1 decision as a bonus. **Chosen: (A).** Reasoning: `resolveUploadActor` is the shared seam every write route in this API goes through (actor/slug resolution, JSON-body parsing, error-to-HTTP mapping); this route already carries a deliberate, documented justification for staying on the shared `mode:"write"` seam (a Clerk-session/`arp_`-key/OAuth caller reaching this endpoint is benign — the issued token is a strict subset of capability that caller already holds, never an escalation) — reversing that without a new forcing reason would be scope creep on a security-critical change, not a simplification. Critically, (B) would NOT have avoided the header re-read anyway: `WriteRunContext`/`UploadActor` carry no raw claims (by design — `sub` on a refreshed token must always come from the LIVE `loadWritableReport` re-check, never echoed from presented claims), so recovering `sessionStart` requires reading the `Authorization` header directly regardless of which front door authenticated `actor`. (A) achieves the goal (bound the refresh chain) with zero ripple into `resolveUploadActor`/`UploadActor`, used by every other write endpoint. New helper `resolvePresentedSession` (`edit-token-refresh.server.ts`) does the independent read + `readEditToken` call; a caller that presents NO edit token at all (`resolveUploadActor` authenticated via Clerk/`arp_`/OAuth instead) has no chain to bound, so the refresh simply STARTS a fresh session (`sessionStart = now`) — those credentials aren't the leaked-bearer-token risk this cap targets.
  - **Tests**: `packages/domain/src/edit-token.test.ts` — `mintEditToken` defaults `sessionStart` to now and honors an explicit value; a legacy (no-`sessionStart`) token still round-trips/authenticates; tampering with `sessionStart` breaks the signature. `apps/app/app/server/edit-token-refresh.server.test.ts` — within the cap refreshes succeed AND carry `sessionStart` forward unchanged (not reset); at/past the cap boundary denies; a legacy presented token (`sessionStart: undefined`) denies; the no-edit-token (fresh-session) path succeeds with `sessionStart = now`; the pre-existing live-canWrite deny matrix (revoked/outsider/lost-ownership/deleted/nonexistent) is unchanged and still passes with the new 4th `presented` parameter; `resolvePresentedSession` itself is covered for valid/missing/wrong-secret/expired/legacy tokens.

- **Phase 5-F — the ACTUAL P0 root cause: the `/edit` route was flat-route-nested under the public viewer (fixed, PR #188).** The owner-unlock-wall diagnosed in Phase 5-E was NOT a secret misalignment (both origins had the aligned secret; `/health` on both confirmed the correct commit was live). So `GET /:slug/edit` ran the PARENT public-viewer loader FIRST, which 302s any private report to `${appOrigin}/unlock/{slug}` **before the editor loader ever executed** — the unified editor was structurally unreachable for every private report, from #184 (which added the route) onward. Confirmed live: `/:slug/edit` returned a single-hop 302 to `${appOrigin}/unlock/{slug}` carrying the public viewer's `viewHeaders()` CSP, proving `$slug.tsx` handled it. **Fix:** rename `$slug.edit.tsx` → `$slug_.edit.tsx`; the trailing `_` opts the segment out of flat-route nesting, making `/:slug/edit` a top-level sibling route whose loader runs directly (`remix routes` after: `<Route path=":slug/edit" />` top-level). - **Phase 5-G — the owner fallback did not survive its own hand-off, and every post-capability degrade was silent (fixed, `fix/owner-lockout`).** A second production owner lockout, 2026-08-06: two PRIVATE reports, same owner, same Clerk session, same deployments, minutes apart. Both got an identical app-side mint (`ownerFallbackMinted: true`) and an identical `303` on `GET /{slug}/edit?et=…&oa=…`; the follow-up `GET /{slug}/edit` carrying the cookie then served `200` for one and `302`'d to the bare `/{slug}` for the other → `${appOrigin}/unlock/{slug}` → `403 "This report is private — only its owner can view it."` (that page now answers a uniform `404` for every denial — ADR-0056) The `owner-edit-degraded-to-view` signal Phase 5-E added never fired. Three defects, all in the same seam:
  - **The `oa=` fallback dies at the 303.** `ownerOpenLocation` delivers it ONCE, on the query string. The 303 that redeems `et=` into the `arp_edit` cookie deliberately strips the query — so on the second (cookie-only) request `oa` is structurally absent, and every degrade there resolved to the bare `/${slug}`. Phase 5-E's `degradeLocation(slug, oa)` therefore only ever protected an owner on the FIRST request, the one hop where the round-trip was least likely to fail. **Fix:** persist it as its own `arp_edit_oa` cookie at 303 time — same `Path=/${slug}/edit` scoping, same `Max-Age` as the edit cookie — and read `oa` from the query OR that cookie. **Exposure WIDENS, deliberately and boundedly** — an earlier draft of this record claimed it "strictly DECREASES", which was false (review #247 H-3). Nothing was removed: `ownerOpenLocation` still appends `&oa=` to the query, so the address-bar / history / referer hop is unchanged. What is ADDED is an HttpOnly cookie COPY of the token, plus five further reachable occasions on which the 24h `owner:true` token is emitted into a URL as `?access=` (`app-origin-unset`, `lookup-failed`, `no-servable-version`, the route's document-load failures, and — defensively, unreachable today — `gate-decision-unusable`), where before only the `denied` branch of the FIRST request could do it: **redeeming paths go from one to six**. Each such redemption mints an `arp_unlock` cookie at the BROADER `Path=/${slug}` with `Max-Age = claims.exp - now`, i.e. up to the token's full 24h — so the practical redemption window widens from a single request to the whole edit session and beyond. The trade is worth making (the alternative is an owner locked out of their own report) and is bounded by five mitigations: (1) the fallback is **verified, not trusted** — `acceptOwnerFallback` requires a valid HMAC, this slug, an unexpired token and `owner === true`, plus a 1 KiB length cap (review #247 H-1); (2) `Path=/${slug}/edit`, so it is never sent on the public `GET /<slug>` read; (3) `Max-Age` tied to the EDIT token's remaining life (≤15 min), so the cookie copy dies with the edit session even though the token itself lives 24h; (4) HttpOnly + Secure + SameSite=Lax; (5) percent-encoded, so the value can never split the `Set-Cookie` header. Shortening `OWNER_TTL_SECONDS` is the lever if this window is judged too wide. `Decision.setCookieAndRedirect` consequently carries `cookies: readonly string[]` (routes must `append`, never `set`).
  - **Every degrade now routes an owner through `?access=`, not just the denied branch.** Phase 5-E explicitly scoped the fallback to `resolveEditAccess → denied` and left the other call sites (missing `appOrigin`, non-`"serve"` outcome, blob-read failure, malformed shell) on the bare `/${slug}` — "matching the reported failure mode exactly". That scoping is what this incident exploited: the failure was post-capability, so it took one of exactly those untouched paths. `Decision.serve` carries `degradeTo`/`ownerFallback` so a route-side failure lands where the gate's own degrades do. (Superseded in part by the review-#247 amendments below: the route's DOCUMENT failures no longer degrade at all — they render an explanatory page — so `degradeTo`'s remaining consumer is the route's defensive-narrowing branch.)
  - **Observability: `edit-degraded-to-view` (new) alongside `owner-edit-degraded-to-view`, both with a `reason`.** The Phase 5-E signal was emitted INSIDE `if (oa)`, so it could not fire on the very request where `oa` was structurally unavailable — the incident produced a 302 with zero log lines on the view origin. Every degrade off `/edit` now emits one line, with a `reason` of `edit-token-denied` / `app-origin-unset` / `no-servable-version` / `lookup-failed` / `gate-decision-unusable` — plus, on a THIRD event (`edit-document-unopenable`, see the amendments below), `document-unreadable` / `document-unsplittable` / `document-unparsable`, which no longer degrade to the view at all. The `owner-…` event name is retained for the owner case (it is what incident queries look for); the funnel to `/open` stays unlogged — it is the happy path for an expired cookie, not a degrade.
  - **`loadEditableDocument` (`apps/view/app/edit/load-document.ts`)** extracts the route's document-load step so the two remaining "authorized but can't render" failures are unit-testable and named. Note the asymmetry it makes explicit: uploads are stored VERBATIM (`HtmlBundleProcessor`), and the read-only viewer just streams bytes, so a document with no `<body>` VIEWS perfectly and cannot be opened by the editor at all — "views fine, won't edit" is an expected, reportable state. A corrupt `_source.json` sidecar also no longer 500s the route (it was an uncaught `JSON.parse`); it falls back to parsing the body and logs `edit-source-sidecar-unparsable`.
  - **Not established without production access:** WHICH of `document-unreadable` / `document-unsplittable` / `document-unparsable` fired for the incident report. Both were silent, both produce the identical observed `302 → /{slug}`, and both are per-report (the working report had one 126-byte version, the broken one a 46,984-byte live version). The gate's own branches are excluded by the BROKEN report's own follow-up hop, not by the working report: `GET /{slug}` returned **`302`, not `404`**, so `resolveViewableReport` returned `serve`/`scanning` for that slug — never `notfound` — which retires `no-servable-version` and `lookup-failed` for the report that actually failed. (Both versions were `scan_status: clean` and uploaded ~14h earlier, so nothing was mid-scan.) The working report's `200` proves `APP_ORIGIN` is configured on the view deployment and the secret is aligned, which retires `app-origin-unset` and the PR #185 secret-misalignment class — but shared code alone would NOT have excluded a per-report `no-servable-version` outcome, so that argument is the weaker of the two and is not what carries the exclusion. The new `reason` field is what will name it on the next occurrence.
  - **Review #247 amendments (same branch, before merge).** Four corrections to the above, each closing a hole the first pass left:
    - **The `oa=` fallback is VERIFIED, not trusted.** It was read straight off the query, written verbatim into `Set-Cookie`, and used as `ownerFallback: oa !== undefined` — the flag that selects the `owner-edit-degraded-to-view` event. So a write-grantee (valid `et=`, for whom `ownerOpenLocation` deliberately never mints an `oa`) could append `&oa=anything` and forge the exact incident signal this seam exists to produce, and park unbounded bytes in the cookie jar. No privilege escalation — redemption was always verified downstream by `resolveAccessDecision` — but a forgeable signal is worse than no signal. `acceptOwnerFallback` (`gate.server.ts`) now applies the redeemer's own check up front: valid HMAC, this slug, unexpired, `owner === true`, plus a 1 KiB length cap checked BEFORE the HMAC, failing closed on an unset secret.
    - **A third document reason, `document-unparsable`.** `parseBody` was the only unguarded call left in `loadEditableDocument` — a function whose whole contract is "never crash, always name a reason" — and it runs linkedom plus ProseMirror's RECURSIVE DOM parse, which a deeply nested document overflows outright. It is also the line taken by every report with no `_source.json` sidecar, i.e. every uploaded-never-edited report: exactly the incident report's profile. Separately, the sidecar guard caught malformed JSON but not wrong SHAPE (`null`, `[]`, `42`, `{}` all survive `JSON.parse(...) as PMDocJson` and then throw in `PMNode.fromJSON` at MOUNT, past every server-side degrade), and its warning now carries `slug` so it correlates with the degrade line from the same request.
    - **The version-diff endpoint degrades too.** `report-diff-loader.server.ts` still called `splitShell` unguarded, so the same "views fine, won't edit" document that the view origin now names `document-unsplittable` still 500'd `GET /api/v1/reports/{slug}/diff` — the endpoint the editor's Versions/Compare panel calls. It returns the same structured error the neighbouring "a version's HTML is missing" guard returns. The third `splitShell` site, `reassembleEditedHtml`, stays unguarded on purpose: it only ever runs on a document the editor already opened.
    - **One degrade target, `degradeTargetFor`.** The `/edit` loader had two answers to "where do I send someone I can't render for?": `decision.degradeTo` for its document-load failures, and a hard-coded `/${slug}` — silently, no log line — in the branch narrowing past Decision shapes the edit purpose cannot produce. That is the same "left one branch untouched" pattern this phase criticises Phase 5-E for. `degradeTargetFor` is now the one answer for every Decision shape, and the defensive branch emits `gate-decision-unusable`.
    - **A document failure now RENDERS a page; it does not redirect at all (operator-approved, 2026-08-06).** The three `document-*` reasons fire AFTER the gate has returned `serve` against a valid `arp_edit` cookie — the capability is already proven, so `/edit` is entitled to answer on the view origin with its own content. The old `302` to the read-only viewer meant an owner clicked Edit, was silently redirected, landed in a read-only viewer with no explanation, and clicking again just repeated it; for a PRIVATE report that viewer bounces on to `/unlock/{slug}`, which is how the lockout completed. Carrying the right `oa` token through that redirect fixes the SYMPTOM; not redirecting removes the path — there is no `Location` to follow, so the unlock wall is unreachable from a document failure by construction rather than by guard. `apps/view/app/edit/unopenable.ts` owns the copy (one distinct sentence per reason, naming the one action that would change the outcome; the reason CODE never appears in user copy) and `UnopenableDocument` renders it. Status **409**, not 200 and not 3xx: the request was understood and authorized but could not be completed, and the conflict is with the target resource's current state, which the user can resolve and resubmit (re-upload an editable document) — a 200 would report to every probe and log query that editing worked. Contrast the ADR-0038 §2 scanning holding page, which IS a 200 because that state clears on its own. Headers are `editViewHeaders({appOrigin})` — the same ADR-013 stack the editor render uses, since this is the same route's own first-party Remix document, carrying strictly less (no report bytes, no edit token); `viewHeaders()` would be wrong, its top-level `sandbox` CSP exists for the untrusted report on `GET /<slug>`. The log line is a DISTINCT event, `edit-document-unopenable`, keeping the same `reason` values: `*-degraded-to-view` naming an outcome that never reaches the view is the same drift this phase exists to remove, and the two are operationally different — a degrade is the incident class (an owner silently stranded), this is a handled outcome the user was told about. The measurement question above is still answerable off the `reason` field.
    - **`deniedEdit` funnels a REJECTED token before it degrades an owner.** The branch answered `if (oa)` BEFORE the `${appOrigin}/reports/{slug}/open` funnel. That was safe while `oa` could only arrive on a query — it was then present exactly once, on the request that had just been minted, and could only describe THAT hand-off failing. Cookie-carrying it (this phase) changed the reachability: `oa` survives the whole edit session, so it also catches every LATER denial — an expired `arp_edit`, a since-rotated secret, clock skew. Each of those is a token that was PRESENTED and did not verify, and each is repaired by exactly one thing: a fresh mint. Degrading them to read-only removed the recovery path in precisely the secret-rotation scenario Phase 5-E exists for, and parked a still-entitled owner in read-only for the fallback's remaining 24h. The gate now distinguishes a **rejection** (a token verified and failed) from an **absence** (no token, or no secret to judge one with), and routes them: *rejected* + funnel available → **funnel**, even with a verified `oa`; *absent* + verified `oa` → the **`oa` degrade**, unchanged (nothing was rejected, so nothing points at the round-trip, and the `oa` in hand is a working read-only capability rather than another hop's gamble); *no funnel* (no secret / no `appOrigin`) → the `oa` degrade if one is in hand, else the bare viewer — this is what keeps the unlock wall unreachable when `APP_ORIGIN` is unset. This deliberately EXTENDS the PR #185 residual redirect loop (both secrets set but MISALIGNED) to owners, and that is the point: a loop the browser surfaces and the operator can see beats an owner quietly parked in read-only, which is how this incident stayed invisible.
  - **Tests**: `apps/view/app/server/gate.server.test.ts` — the cookie-carried `oa` matrix (every degrade × owner-fallback-present, the `?et=` hand-off setting both cookies, query `oa` superseding a cookie one, an empty `arp_edit_oa` treated as absent, `degradeTo`/`ownerFallback` on `serve`) and a `reason` assertion per degrade. `apps/view/app/edit/load-document.test.ts` — missing blob, blob error, no `<body>`, unclosed `<body>`, a bare fragment, a 50k-deep body that overflows the ProseMirror parse, sidecar preference and every wrong sidecar SHAPE. `apps/view/app/edit/unopenable.test.ts` — the page is a 4xx and never a 3xx, distinct non-leaking copy per reason, a root-relative read-only link, and no capability in the payload. `gate.server.test.ts` additionally pins the rejection-vs-absence routing: a rejected token funnels even with `oa`, an expired `arp_edit` alongside the `oa` cookie funnels, and both fall back to the `oa` degrade when `appOrigin` is unset.

- **Phase 5-H — the unopenable page's read-only link had no capability, so the owner could learn why but still not read (fixed, `fix/unopenable-readonly`).** Measured in production on `f83ed59`, with both #247 and #248 deployed. The operator's own `acl: private`, `editability: "unsplittable"` report reached the new 409 page correctly and the new owner-aware `/unlock/{slug}` recognised them correctly — both Phase 5-G improvements working exactly as designed. But the 409 page's one forward action, **"Open the read-only view"**, was a bare `href="/{slug}"`. For a PRIVATE report that link cannot work: the plain viewer sees private with no token and redirects to `${appOrigin}/unlock/{slug}`, whose owner-aware page offers `/reports/{slug}/open`, which mints and hands off to `/edit`, which renders the same 409 page, which offers the same bare link. Every hop is an improvement over what preceded it and the composition is a cycle that never reaches the content — so the owner of a private, unopenable report could read a clear explanation of why they could not EDIT it and still could not READ it. That is the original complaint ("my own reports are private for myself") in its last remaining form, and it is the same failure shape Phase 5-G named: *the fallback dies at one hop and nobody notices*.
  - **The page carries the gate's OWN degrade target.** `unopenableDocument` takes a `readOnlyHref` and the `/edit` loader passes `degradeTargetFor(decision, slug).to` — `/{slug}?access=<oa>` when the gate verified an owner fallback, `/{slug}` when it did not. **Nothing is minted here.** The view origin stays credential-free (ADR-0056's keystone: the app authorizes, the viewer verifies); the `oa` is the one the visitor themselves presented on this request (query or `arp_edit_oa` cookie) and that `acceptOwnerFallback` already verified — HMAC, this slug, unexpired, `owner === true`. An unverified `oa` never becomes a `degradeTo`, so it can never become an `href` either. A **write-grantee** keeps the bare link, which is correct for them: `ownerOpenLocation` deliberately never mints them an `oa`, and the unlock page they land on recognises write access (Phase 5-G).
  - **One destination, not two.** A `Location` the browser follows and an `href` the user clicks want the identical answer to "where do I send someone I cannot render for?". Review #247's `degradeTargetFor` exists precisely to stop that question having two answers; this page had quietly become the second one. The `serve` Decision's `degradeTo` doc comment — which had come to claim the document failures no longer consume it — is corrected to say they consume it as an `href` rather than a `Location`.
  - **The invariant is enforced, not assumed.** `readOnlyHref` now arrives from a caller, so `unopenable.ts` collapses anything that is not an unambiguous root-relative path (absolute, protocol-relative, `/\`-relative — which some browsers normalise to `//` — or any scheme URL) back to `/{slug}`. The type always documented "ALWAYS a root-relative path"; before this change that was true by construction, and it now has to be true by check.
  - **`editUnopenableLine` gains `ownerFallback`** (the boolean; never the token). Without it the line cannot distinguish "an owner was told why and can still read their report" from the production shape above. The reason vocabulary is unchanged, so the open question this line was introduced to answer is still answerable off it.
  - **DECIDED: an unopenable report does NOT get special routing (`editability` stays advisory).** The obvious-looking alternative was to send an owner of an `editability: "unsplittable"` report straight to the read-only view from `/unlock` or from `ownerOpenLocation`, skipping the editor hand-off that cannot succeed. Rejected — see ADR-0080 §4, which this reaffirms with the concrete case. Four reasons: (a) ADR-0080 §4 already forbids gating on the column, because a stale or wrong verdict then locks a user out of a report they can actually edit, reintroducing the incident from the other side; (b) `editability` is `null` for the entire pre-ADR-0080 corpus, so routing on it would fix the cycle only for reports uploaded after 2026-08-06 and leave every existing report in it — not a fix for the incident that motivated it; (c) the verdict is computed at WRITE time from the bytes, while the editor's ability to open them is decided at READ time, and the 409 page cannot make that mistake because it fires only when the editor actually failed, on those bytes, just now; (d) `/reports/{slug}/open` is the ONE edit-token mint (ADR-0059 §4) and `/unlock` deliberately links to it rather than deciding anything itself (`private-unlock.server.ts`) — putting a content-shaped predicate inside that seam gives it a second job. With the link fixed the cycle terminates on its own: unlock → open → `/edit` → 409 page → `/{slug}?access=<oa>` → grant → `arp_unlock` cookie → 303 → the report. One extra hop, always terminating, and the user is told why on the way through.
  - **Sibling-gap sweep** (the point of #247 being that one untouched branch is how this class survives): every other builder of a viewer URL was checked. `ownerOpenLocation`'s no-secret fall-through (`${viewOrigin}/${slug}`) has no token to carry — that is its fail-closed posture. `/unlock`'s public-mode `redirectToView` needs none. `view_url` on the `201` upload response and the dashboard's upload confirmation are deliberately credential-free permanent share links; embedding a 24h `owner:true` token in either would be a real leak. `degradeTargetFor`'s non-`serve` arms are unreachable for the edit purpose and hold no `oa` by construction. The 409 page was the only one.
